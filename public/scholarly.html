Abstract

LittleSteps este o aplicație web de tip Single Page Application (SPA) destinată gestionării activităților pediatrice zilnice — alimentație, somn, schimburi de scutece, istoricul medical, vaccinuri și evoluție ponderală. Sistemul adoptă o arhitectură decuplată: un front-end HTML5/CSS3/JavaScript pur comunică asincron cu un strat de servicii RESTful implementat în PHP Vanilla, persistând datele într-un motor SQLite izolat prin strategia Multi-Tenant bazată pe family_id. Raportul de față descrie cerințele sistemului, arhitectura componentelor, modelul relațional al datelor și măsurile de securitate implementate conform ghidurilor OWASP.

Secțiunea 1

Introducere și Motivație

Urmărirea activităților unui nou-născut constituie o provocare cognitivă semnificativă pentru părinți, în special în primele luni de viață, când frecvența și regularitatea alăptărilor, somnului și schimburilor de scutece sunt indicatori medicali esențiali. Soluțiile existente pe piață — aplicații mobile native — impun bariere tehnologice și de cost care le limitează accesibilitatea.

LittleSteps adresează această problemă printr-o soluție web progresivă, accesibilă pe orice dispozitiv cu browser modern, fără instalare, cu suport pentru mai mulți membri ai familiei și cu posibilitatea exportului datelor în formate deschise (JSON, CSV) și a abonamentului la un flux RSS în timp real.

Din perspectivă tehnică, proiectul demonstrează că o arhitectură SPA robustă poate fi implementată exclusiv cu tehnologii web native — fără framework-uri JavaScript de tip React sau Vue — menținând totodată standarde ridicate de securitate, performanță și experiență utilizator.

Secțiunea 2

Specificarea Cerințelor Sistem

Conform machetei IEEE 830 System Requirements Specification, cerințele sunt clasificate în cerințe funcționale (FR) și non-funcționale (NFR).

2.1 Cerințe Funcționale

FR-01
Autentificare Multi-Rol
Sistemul va suporta trei roluri: admin, family_admin și member, cu privilegii distincte per rol.
FR-02
Jurnal Timeline
Utilizatorul va putea înregistra și vizualiza în ordine cronologică activitățile copilului activ selectat.
FR-03
Tracker Alimentație
Aplicația va înregistra mesele cu detalii despre tip (sân, formulă, solid) și cantitate.
FR-04
Tracker Somn
Cronometrul de somn va persista starea în localStorage pentru rezistență la reîncărcarea paginii.
FR-05
Istoric Medical
Modulul va permite stocarea consultațiilor, medicamentelor și observațiilor medicale cu marcaj temporal.
FR-06
Galerie Media
Sistemul va accepta upload multipart de imagini, stocate fizic în public/assets/uploads/.
FR-07
Export Date
Utilizatorul va putea descărca toate activitățile în format JSON sau CSV, respectiv se va putea abona la un flux RSS/XML valid.
FR-08
Administrare Familie
Adminul va gestiona membrii familiei: adăugare, modificare rol și ștergere permanentă din sistem.

2.2 Cerințe Non-Funcționale

  • ⚡
    NFR-01 Performanță: Timpul de răspuns al API-ului pentru operații CRUD simple nu va depăși 200ms pe conexiuni medii (5 Mbps).
  • 📱
    NFR-02 Responsivitate: Interfața va fi utilizabilă pe ecrane de minim 320px lățime, respectând specificațiile CSS Media Queries Level 4.
  • 🔒
    NFR-03 Securitate: Toate interogările SQL vor utiliza Prepared Statements (PDO). Nu vor exista endpoint-uri accesibile fără validarea sesiunii.
  • 🌐
    NFR-04 Portabilitate: Aplicația va funcționa în orice browser modern (Chrome 100+, Firefox 100+, Safari 15+) fără dependențe externe CDN.
  • ♿
    NFR-05 Accesibilitate: Elementele interactive vor respecta atributele ARIA, iar contrastul textului va respecta standardele WCAG 2.1 AA.

Secțiunea 3

Arhitectura Sistemului

LittleSteps adoptă un model arhitectural în două straturi principale, separate prin interfața HTTP/JSON: stratul client (SPA) și stratul server (RESTful Services).

3.1 Stratul Client — Single Page Application

Fișierul index.html constituie punctul unic de intrare al aplicației. Navigarea între module (Timeline, Medical, Dentiție, Evoluție, Vaccinuri, Galerie, Familie, Export, Admin) este gestionată exclusiv prin funcția JavaScript showSection(), care manipulează proprietatea CSS display a secțiunilor relevante fără a produce nicio reîncărcare a paginii.

Motorul de procesare app.js implementează gestiunea asincronismului dual prin Promise.all(), permițând apeluri paralele la multiple endpoint-uri API. Graficele interactive de evoluție ponderală sunt realizate cu biblioteca Chart.js (inclusă local), iar tema vizuală Dark/Light este persistată în localStorage prin variabile CSS rădăcină.

3.2 Stratul Server — RESTful PHP Vanilla

Fiecare resursă a sistemului este expusă printr-un fișier PHP dedicat din directorul /api/. Funcția centralizată sendResponse() din api_helper.php garantează că toate răspunsurile au antetul Content-Type: application/json; charset=UTF-8, prevenind inconsistențele de codificare. Datele din corpul cererilor POST sunt decodate cu getJsonInput(), care citește direct php://input — compatibil cu orice client REST.

Baza de date database.sqlite conține șapte tabele normalizate (3NF). Izolarea Multi-Tenant este implementată prin coloana family_id, prezentă în toate tabelele de date, garantând că niciun utilizator nu poate accesa datele altei familii.

Secțiunea 5

Securitate — Conformitate OWASP Top 10

  • 🛡️
    A03 — SQL Injection: Toate interogările SQL utilizează exclusiv Prepared Statements prin extensia PDO a PHP. Niciun parametru de utilizator nu este interpolat direct în șiruri SQL.
  • 🔐
    A02 — Autentificare: Parolele sunt stocate exclusiv ca hash-uri BCRYPT cu cost factor implicit (10). Sesiunile PHP sunt regenerate după autentificare (session_regenerate_id()).
  • 🧱
    A01 — Broken Access Control: Fiecare endpoint API verifică ['user_id'] înainte de orice operație. Endpoint-urile administrative verifică suplimentar rolul admin / family_admin.
  • ✏️
    A07 — XSS: Toate datele provenite din API sunt randate în DOM exclusiv prin element.innerText sau element.textContent, prevenind execuția de markup arbitrar.
  • 🏠
    Multi-Tenant Isolation: Clauza WHERE family_id = :fid este prezentă în toate interogările de citire, garantând că utilizatorii dintr-o familie nu pot vizualiza datele altei familii.

Secțiunea 6

Design UI/UX — Interfață Web Responsivă

Interfața respectă principiile Responsive Web Design (RWD) prin utilizarea sistemului Flexbox pentru layout-uri fluide și CSS Grid pentru aranjamente bidimensionale. Breakpoint-urile sunt definite cu Media Queries la 768px (tabletă) și 480px (mobil).

Paleta cromatică adopată este bipolară: un ton violet profund (#6c5ce7) ca accent primar, pe fundal neutru deschis (#f5f6fa), cu suport complet pentru modul întunecat implementat prin variabile CSS :root și [data-theme="dark"]. Tranziția între teme este persistată în localStorage și aplicată înainte de randarea DOM-ului, prevenind flash-ul vizual.

Componentele vizuale — carduri, butoane, badges, timeline items — sunt construite cu border-radius consistent (8-12px), umbre subtile (box-shadow: 0 2px 8px rgba(0,0,0,0.06)) și animații de hover la 200ms, conferind o experiență modernă fără a recurge la librării CSS externe.

Secțiunea 7

Interoperabilitate și Date Deschise

LittleSteps implementează două mecanisme de interoperabilitate, respectând principiile datelor deschise (Open Data):

  • 📦
    Export JSON / CSV: Endpoint-ul /api/export.php generează asincron un fișier complet al tuturor activităților copilului activ, descărcat direct de browser cu antetele HTTP corespunzătoare (Content-Disposition: attachment).
  • 📡
    Flux RSS 2.0: Endpoint-ul /api/rss.php generează în timp real un document XML valid RSS 2.0, permițând integrarea cu orice agregator de știri sau serviciu de notificare extern.

Secțiunea 8

Concluzii

LittleSteps demonstrează că o aplicație web complexă, cu funcționalități multiple și cerințe de securitate ridicate, poate fi implementată eficient cu tehnologii web native, fără dependențe de framework-uri grele. Arhitectura SPA + REST PHP Vanilla + SQLite oferă un raport excelent performanță/complexitate pentru aplicații de uz familial cu volum moderat de date.

Direcțiile de dezvoltare viitoare includ: implementarea unui Service Worker pentru funcționalitate offline (PWA), notificări push pentru programul de vaccinare și exportul datelor în format HL7 FHIR pentru interoperabilitate cu sisteme medicale electronice.
